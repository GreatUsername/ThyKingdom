# Цикл симуляции

Как устроен шаг симуляции и как в него попадают изменения игрока. Записано со слов автора; следствия для рубежей — в [[02 Milestones]], для решений — в [[05 Open decisions]].

## Как устроено

1. **Поток таймера.** Следит за машинным временем и бросает callback, когда машинное время изменилось на величину, заданную при запуске приложения.
2. **Рабочий поток.** Получает callback и считает, сколько ждать до начала следующего шага симуляции.
3. **Шаг симуляции.** По истечении ожидания выполняется шаг.
4. **Замер.** По завершении шага рабочий поток измеряет, сколько шаг занял, сохраняет значение, засыпает до следующего callback.
5. **Окно изменений.** Между шагами состояние игры может меняться, и изменения применяются до следующего шага. Пока шаг выполняется, изменения игрока копятся в очереди; из очереди они применяются в промежутке между шагами.
## Слои

Пять целей, и направление зависимостей между ними — не стиль, а действующее правило: чего нет в зависимости, того нельзя и использовать.

| Слой      | Что это                                   | Зависит от                    |
| --------- | ----------------------------------------- | ----------------------------- |
| `core`    | симуляция: часы, мир, подсистемы, оценщик | только стандартная библиотека |
| `config`  | настройки игрока                          | `core` — ради разбора INI     |
| `runtime` | планировщик, таймер, источник времени     | `core`                        |
| `runner`  | консольный прогон сценария                | `core`                        |
| `tests`   | проверки                                  | `core`, `config`, `runtime`   |

Две стрелки важны особо. **`core` не зависит от `config`**, поэтому настройка игрока не может дойти до симуляции. **`core` не зависит от `runtime`**, поэтому машинное время не может попасть в шаг. Оба запрета держит компилятор, а не дисциплина: файл ядра не может даже назвать эти типы.

## Потоки

| Поток               | Что делает                                                                    |
| ------------------- | ----------------------------------------------------------------------------- |
| Таймера             | Следит за машинным временем и бросает callback                                |
| Рабочий (симуляция) | Ждёт, выполняет шаг, замеряет длительность, засыпает до следующего callback   |
| UI                  | Живёт отдельно и продолжает работать при паузе                                |
| Отрисовки           | Берёт снимок состояния и строит кадр                                          |

**Снимок состояния для отрисовки.** Когда шаг выполнен, состояние кладётся в потокобезопасную очередь. Поток отрисовки забирает снимок из очереди, когда ему удобно, и строит по нему кадр — это происходит, пока симуляция находится в ожидании. Благодаря этому отрисовка не блокирует симуляцию: блокировки на обновление кадра нет.

**UI живёт в своём потоке.** Поэтому при паузе интерфейс продолжает работать, хотя симуляция живых событий не выполняется.

## Мир как композиция подсистем

`World` — класс, который содержит специализированные классы, реализующие общий базовый интерфейс:

| Подсистема                               | Что содержит                                                  |
| ---------------------------------------- | ------------------------------------------------------------- |
| Поверхность (surface)                    | рельеф, клетки, земля                                         |
| Атмосфера и погода (atmosphere, weather) | температура, осадки, сезоны                                   |
| Объекты (objects)                        | контейнер указателей на базовый класс — все объекты симуляции |

`World` работает с подсистемами через базовый интерфейс и заставляет их выполнять шаг симуляции и взаимодействовать между собой. Логика живёт в подсистемах, а `World` — это координатор.

**Порядок вызова подсистем фиксирован правилом.** Конкретный порядок будет определён позже, когда список специализированных классов сложится: пока он не полон, назначать порядок бессмысленно.

**Взаимодействие подсистем** идёт через базовый интерфейс; обмен параметрами между классами выполняет отдельный специализированный класс. Точный механизм обмена определится вместе со списком классов.

## Статические данные объектов

Свойства объектов описываются **статическими данными** — таблицей определений. Все объекты создаются динамически: в момент создания объект получает ссылку на свою запись в таблице. Так разделяются общие неизменяемые определения и изменяемое состояние экземпляра.

**Три идентификатора, все ради скорости**

| Идентификатор | Назначение                                                         |
| ------------- | ------------------------------------------------------------------ |
| `guid`        | стабильный идентификатор, определяющий статические данные объекта  |
| `type-id`     | компактное число вместо `guid`: ссылаться по числу проще и дешевле |
| `render-id`   | числовой идентификатор для отрисовки                               |

`type-id` и `render-id` намеренно различаются: несколько разных `type-id` могут использовать один набор текстур, если объекты выглядят одинаково.

Второй способ получить ту же информацию — **константные флаги в базовом классе**: `isHuman()`, `isAnimal()`, `realObjectType()` (возвращает `enum` типа объекта) и подобные. Флаги дают дешёвое ветвление и подсказывают, нужно ли приводить объект к более специализированному классу.

**Флаги выводятся из статических данных в момент создания объекта** — либо сравнением идентификатора с типами, которые считаются человеческими, либо чтением соответствующего флага из записи таблицы. Источник истины один — таблица определений, а флаг на объекте это вычисленное один раз значение. Расхождения между флагом и таблицей быть не может, а в шаге симуляции читается готовый флаг, без обращения к таблице.

Следствия:

- Таблица определений — **часть входных данных симуляции.** Её изменение меняет поведение так же, как изменение кода, поэтому в воспроизведении нужно фиксировать её версию или хеш вместе с seed и потоком команд.
- Для M1 таблица должна читаться **без графики**, иначе headless-тесты невозможны (см. ОД-20).
- **Порядок создания объектов — это часть порядка симуляции.** Объекты создаются динамически и попадают в контейнер в порядке создания, поэтому создание должно быть детерминированным.

## Обновление мира внутри шага

Обновление сущностей (юнитов, зданий, ресурсов) идёт очередью. Если при обновлении сущность воздействует на другую сущность, то та, на которую направлено воздействие, кладётся в **очередь повторного обновления**.

Эта очередь вызывается после того, как основная очередь сущностей закончила обновление, — в рамках того же шага. А взаимодействие, возникшее уже при повторном обновлении, будет обработано следующим обновлением мира, то есть при вызове нового шага симуляции.

Схема ограничивает каскад взаимодействий одним дополнительным проходом на шаг и потому остаётся детерминированной.

Очередь не одна. У каждой своё назначение:

| Очередь              | Кто кладёт                                  | Когда разбирается                   |
| -------------------- | ------------------------------------------- | ----------------------------------- |
| Изменения от UI      | UI                                          | между шагами, перед следующим шагом |
| Обновление объектов  | шаг симуляции                               | внутри шага                         |
| Повторное обновление | объекты, воздействовавшие на другие объекты | внутри того же шага, после основной |

### Порядок обхода контейнера объектов

Контейнер объектов хранит объекты **в порядке**, а указатели на базовый класс нужны только для удобного доступа через общий интерфейс. Значит, порядок обхода детерминирован, и это требование выполнено.

Остаётся одно условие, которое стоит держать в голове: **сам порядок вставки должен быть детерминированным.** Он не должен зависеть от значений указателей или от обхода хеш-таблицы с ключом-указателем, иначе адреса, рандомизированные при запуске, снова начнут влиять на симуляцию. Контейнер, хранящий объекты по порядку, этому требованию удовлетворяет.

## Столкновения

Две фазы. На каждом шаге проверяются грубые габаритные боксы объектов (broad phase). Если боксы пересеклись, проверяется точная форма объекта (narrow phase).

**Решено (ОД-20): форма берётся из данных симуляции, а не из модели.** В симуляции хранится простой коллайдер — круг, капсула или бокс. Геометрия модели используется только для отрисовки. Поэтому габаритный бокс для broad phase тоже берётся из коллайдера, а не из модели.

Открытые вопросы:

- **Чем ускоряется broad phase.** Если боксы проверяются попарно, стоимость растёт как квадрат числа объектов. Нужна пространственная структура — сетка, пространственный хэш или подобная.
- **Составные коллайдеры:** нужен ли объекту не один коллайдер, а несколько.
- **Вращается ли коллайдер** вместе с объектом или остаётся осевым.
- **Порядок разрешения столкновений**, когда объектов больше двух, — это тоже порядок симуляции, и он должен быть устойчивым.

### Поведение при столкновении

Решено (ОД-22): поведение выбирается по **типам** столкнувшихся объектов — часть объектов подвижна, часть неподвижна. Базовые модели M1:

| Пара               | Поведение                                   |
| ------------------ | ------------------------------------------- |
| человек ↔ человек  | расталкивание или обход                     |
| человек ↔ животное | один из них отталкивается                   |
| человек ↔ здание   | обход, если только человек не намерен войти |

Если второй объект является **целью** первого, столкновение считается входом, а не препятствием: одних типов для выбора поведения недостаточно.

**Как это выражается в коде.** Поведение берётся из класса объекта: базовый класс отдаёт общий случай (например, подвижность), более специализированный класс — более точную логику, когда она нужна. Плоская таблица по паре типов не нужна. Когда поведение зависит от **второго** объекта, используются константные флаги базового класса (`isHuman()`, `isAnimal()`) и `realObjectType()` — `enum` типа; двойная диспетчеризация не требуется.

Оттолкнутый объект кладётся в очередь повторного обновления — это и есть её назначение: каскад от отталкивания ограничивается одним дополнительным проходом на шаг.

## Снимок для отрисовки

Потоку отрисовки не нужен объект целиком и все его данные. Нужна **определённая структура данных**, заполненная параметрами объекта: координаты, идентификатор, по которому отрисовка находит свои данные, каналы для разных анимаций и так далее. То есть снимок — это массив компактных структур, а не массив объектов.

Это меняет оценку стоимости: дорогой была бы копия объектов, а копия компактных структур дёшева. Поэтому полный снимок мира вполне может оказаться приемлемым, и фильтрация по области обзора может не понадобиться вовсе — её стоит добавлять по результатам профилирования.

Полезное следствие: идентификатор в структуре означает, что **связь с артом живёт на стороне отрисовки**, а симуляция про текстуры и модели не знает. Тот же принцип применим и к форме для столкновений — см. ОД-20.

Что остаётся открытым:

- **Что включать в снимок:** все объекты или только область обзора. Мысль автора — область обзора; но при компактной структуре полный снимок может оказаться и проще, и не дороже.
- **Мини-карта и метки за экраном** требуют общей картины мира, даже если детальный снимок делается по области.
- Снимок делается **вне шага**, во время ожидания, и является копией: поток отрисовки читает его, пока симуляция продолжает менять состояние.

Варианты — в [[05 Open decisions]], ОД-21.

## Что из этого следует

**Пауза — это отсутствие шагов.** Это состояние цикла, а не игровое правило: шаги просто не планируются. Поэтому пауза ничего не стоит и не требует отдельных механик. См. ОД-16.

**Ускорение — это изменение расписания, а не правил.** N шагов остаются N шагами, как бы быстро они ни выполнялись.

**Приказы не трогают состояние напрямую.** Единственный вход в состояние — очередь, разбираемая на границе шага. Значит, порядок разбора обязан быть детерминированным (например, FIFO с устойчивым разрешением совпадений).

**Запрет приказов во время ускорения — это правило игры, а не ограничение движка.** Очередь технически принимает изменения в любой момент, включая ускорение. Запрет из ОД-14 накладывается сверху, на уровне UI и правил.

## Пауза

Реализуется флагом в состоянии игры. После того как callback получен и ожидание истекло, цикл перед шагом проверяет флаг: если состояние помечено как приостановленное, симуляция живых событий не выполняется — шаг пропускается.

Отсюда два полезных свойства:

- **Пауза — решение на границе шага.** Она не может застать шаг в середине, поэтому не портит состояние и не требует отдельных правил.
- **Пауза не обязана попадать в лог команд.** Она меняет расписание, а не содержимое шагов; при отсчёте игрового времени по числу шагов воспроизведение от неё не зависит.

Цикл живых событий при паузе не двигается вперёд вообще: шаги не выполняются, игровое время не течёт. Работает только UI — потому что он живёт в своём потоке.

Задержка срабатывания паузы ограничена одним интервалом шага.

## Единственное правило, без которого всё рассыпается

> **Игровое время обязано быть функцией числа шагов, а не машинного времени.**

**Подтверждено автором.** События, которые зависят от течения времени, считаются по **игровому** времени. Игровое время прирастает на `dt` при вычислении нового шага. Машинное время используется только для получения callback. Поэтому оба запрета ниже выполняются устройством цикла, а не договорённостью.

Если это выполнено, то пауза, 1× и N× — одна и та же симуляция с разным расписанием, и результат у них совпадает. Это и есть требование «корректной связи времени и событий» из [[Время в игре]], выраженное проверяемо.

Отсюда два запрета:

1. Внутри шага симуляции нельзя читать машинное время. Любое «растёт три реальные секунды» ломает воспроизводимость и делает ускорение меняющим результат.
2. Замеренная длительность шага (пункт 4) годится для диагностики и планирования, но не может влиять ни на состояние игры, ни на число выполняемых шагов.

**Как запрет обеспечен.** Игровое время выдаёт отдельный класс — `World` или класс времени; системы берут время у него, а не у машинных часов. Тогда машинное время системам просто не передано, и запрет выполняется устройством, а не дисциплиной.

**Второе правило того же веса.** Поведение системы должно быть одинаковым в обеих фазах — и при обычном ходе, и при ускорении. Различаться может только **количество за шаг**: сколько продукции выработано, сколько пути пройдено. Если поведение зависит от фазы, значит система не готова к переменному `dt`, и это дефект системы, а не особенность ускорения.

## Частота шага

Частота определяется **перед запуском игры**, по характеристикам производительности машины (ОД-17). Одна игровая секунда во время хода равна одной реальной секунде, но симулируется не одним шагом, а частотой шагов: при 60 Гц — 60 шагов за игровую секунду.

Отсюда шаг игрового времени был бы равен `1 / частота`. **Но по ОД-18 из частоты шаг не выводится:** шаг фиксирован в данных, а частота — это такт, то есть сколько шагов машина успевает выполнить за реальную секунду.

Следствие: при фиксированном шаге прогон переносится между машинами как `(seed + поток команд + число шагов)`. Мультиплееру (статус `parked`) понадобилась бы общая фиксированная частота.

### Шаг и такт — это два разных параметра

| Параметр   | Что задаёт                                    | Может зависеть от машины          |
| ---------- | --------------------------------------------- | --------------------------------- |
| Шаг (`dt`) | сколько игрового времени прибавляет один шаг  | **нет**, иначе симуляция разная   |
| Такт       | сколько шагов выполняется за реальную секунду | да, это и есть производительность |

**Решено (ОД-18): шаг фиксируется в данных, от машины зависит только такт.** Симуляция становится одинаковой везде: слабая машина просто реже выполняет те же самые шаги.

Что остаётся решить — уже не вопрос детерминизма, а вопрос поведения при нехватке производительности: замедление игрового времени, догоняющие шаги или минимальные требования. Варианты и рекомендация — в [[05 Open decisions]], ОД-19.

**Частота шага не связана с частотой кадров.** Сколько шагов в секунду — свойство симуляции, а не монитора: иначе два игрока на 60 и 144 Гц получали бы разные миры из одного seed, а запись прогона была бы верна только на той машине, где сделана. Шаг задаётся данными (ОД-18), а планировщик в `runtime` накапливает реальное прошедшее время и выдаёт целые шаги. Сумма шагов за срок зависит только от суммы прошедшего времени и `dt`, а не от того, как часто планировщик дёргали. Долгая задержка целиком не отрабатывается: лишние шаги отбрасываются, и игра отстаёт от реального времени — это честнее и виднее, чем спираль «догнать любой ценой».

**Правило 1:1 относится только к обычной фазе** (механика 86). Во время ускорения соответствие реальному времени не требуется, поэтому там допустим и более крупный шаг: важно, чтобы результат совпал, а не чтобы шагов было столько же.

**Следствие целочисленного времени.** Время хранится в целых микросекундах, поэтому 1:1 точно выполняется только тогда, когда `dt` делит 1 000 000. 60 Гц не представимо: 1/60 секунды — это 16 666,67 мкс. Точны 50 Гц (20 000 мкс), 100 Гц (10 000), 125 Гц (8 000), 200 Гц (5 000). То есть частота шага — это выбор в данных, ограниченный арифметикой, и монитор на него не влияет.

## Многопоточность

Предполагается движок с пулом потоков, разделяющий задачи, особенно во время ускорения. Рассматривается `athread` — небольшая библиотека на C++14 с пулом потоков и `ThreadGraph`: задачи описываются графом зависимостей, и порядок выполнения выводится из зависимостей автоматически.

**Что это даёт.** Граф зависимостей хорошо ложится на подсистемы: погода должна посчитаться до посевов, поверхность — до объектов. Зависимости выражаются явно, а не порядком вызовов.

**Чего граф не даёт.** Независимые ветви завершаются в неопределённом порядке. Если две ветви пишут в общее состояние, результат перестаёт воспроизводиться. Поэтому к правилу «порядок обхода — это порядок симуляции» добавляется: **параллельная работа либо владеет непересекающимися частями состояния, либо её результаты применяются в фиксированном порядке.** Иначе пул потоков ломает воспроизводимость тихо.

**Согласование с существующим.** В цикле уже есть потоки таймера, рабочий, UI и отрисовки. Пул добавляет пятый род работы, и его задачи не должны одновременно касаться очереди снимков и очереди команд.

**О выборе библиотеки.** `athread` — небольшая библиотека одного автора (2025, Apache 2.0, C++14). Её README прямо предлагает копировать исходники в проект, что снимает вопрос зависимости. Для проекта, который планируется к выпуску, стоит отдельно решить, достаточно ли этого, или надёжнее взять исходники и поддерживать их самим.

**Зачем пул.** Цель — занять несколько ядер, чтобы шаг считался быстрее. Ускорение не должно достигаться ценой воспроизводимости, поэтому расхождение недопустимо: параллельная работа либо владеет **непересекающимися частями состояния**, либо применяет результаты **в фиксированном порядке** (ОД-34). У графа две стратегии исполнения — последовательная и параллельная, — и результат обязан совпадать: последовательная служит эталоном в тестах, а не режимом игры. Переключателя детерминированности не существует, потому что расхождение не допускается ни в каком режиме.

## Граф взаимодействий

**Зачем граф.** Юниты бывают с разным числом взаимодействий, и у самых связанных — у управляющих — вычисление решения состоит из множества связанных подзадач: что приказать, кому, в каком порядке, что при этом учесть. Граф задаёт зависимости между этими подзадачами и позволяет считать их в оптимальном порядке, не пересчитывая лишнего. Это не уровень подробности и не украшение, а способ организовать вычисление решения.

**Откуда берётся объём вычислений.** У юнита две части:

- **Строгая, по типу.** Часть вычислений задана типом юнита и выполняется всегда. Неподвижному зданию движение не считается вовсе — потому что он неподвижен по типу, а не потому, что его понизили в чём-то. Пропуск не требует новой системы: `flag`, выведенный из статических данных при создании, и специализированные классы дают ровно это.
- **По требованию.** Остальное считается тогда, когда возникает потребность. У юнита есть поведение, предпочтения, потребности и требования; их удовлетворение и порождает взаимодействия.

Поэтому «уровень взаимодействия» — описание, а не ручка и не ранг: он говорит, сколько вычислений требует юнит сейчас, и складывается из типа и активных потребностей. Переходов между уровнями не бывает: меняется не подробность юнита, а набор активных потребностей.

**Требование к графу: порядок обхода не должен менять решение.** Независимые ветви считаются в разном порядке, поэтому граф допустим только тогда, когда итог не зависит от порядка. Если подзадачи комбинируются правилом, чувствительным к порядку, решение управляющего начнёт меняться от прогона к прогону — то же расхождение, что отвергнуто в ОД-34, только внутри одного юнита.

**Проверка.** Один и тот же случай просчитать в нескольких допустимых порядках обхода графа и убедиться, что решение совпадает.

**Случайность в потребностях.** Выбор того, как удовлетворить потребность, должен быть отчасти случаен, иначе поведение выглядит машинным. Случайность берётся **seeded-генератором** — зерно выводится из `guid` юнита, — а не из порядка вычислений. Тогда мир выглядит живым, а прогон остаётся воспроизводимым (ОД-34).

**Из чего складывается зерно, решает, что получится.** Зерно только из `guid` даёт **характер**: юнит склонен вести себя одинаково в каждом прогоне, и это читается как личность. Зерно из `guid` и времени даёт **настроение**: склонность меняется от раза к разу. Оба варианта воспроизводимы; разница в том, сможет ли игрок выучить юнита или нет.

## Как создаётся мир

Мир не разбирает файл сам и не заполняется данными извне. Путь такой:

```
сценарий --loadScenario--> Scenario --buildEvaluator--> IEvaluator --makeStep--> результат
                                                          ├── Clock
                                                          ├── Mode (обычный / ускорение)
                                                          └── World -> подсистемы
```

- **`Scenario`** — разобранные и проверенные данные: из чего мир создаётся (`seed`, начальное содержимое) и как прогон выполняется (число шагов, `dt`, ожидаемый хеш). Данные и ничего больше: состояния мира в нём нет.
- **`Evaluator`** — управляющая оболочка прогона. Держит часы, мир и очередь входных сигналов: принимает сигналы, применяет их на границе шага, переключает режим, продвигает игровое время и вызывает мир. **Часами владеет он, а не мир:** часы — это состояние управления, и владеть ими должен тот, кто управляет состоянием.
- **`World`** — только смоделированные сущности: подсистемы и порядок их вызова. Часов, времени и управления в нём нет, и о том, что снаружи что-то происходит, он не знает.
- **`buildEvaluator`** — порождающий механизм. Создаёт часы, строит мир с подсистемами и возвращает готовый прогон.
- **Мир рождается внутри своего владельца.** `Evaluator` строит `World` прямо в своём поле: `m_world(buildWorld(scenario))`. Гарантированное устранение копий в C++17 означает, что возвращаемый объект создаётся непосредственно в этом поле, и перемещений нет ни одного. Сам `buildWorld` объявлен только в `evaluator.cpp` и снаружи не виден, поэтому «мир, который кто-то создал и выбросил» невозможен по устройству: единственный способ получить мир — получить прогон.
- **`IEvaluator`** — абстрактная основа. Прогонщик и будущий интерфейс работают через неё, а не через конкретный класс. Основа намеренно узкая: между реализациями различается то, *когда* вызывается `makeStep` (таймер, пакетный прогон, воспроизведение записи), а не то, что делает шаг.
- **`runtime::Timer`** — таймер живёт в библиотеке `runtime`, выше ядра, и создаётся **после** `Evaluator`, потому что сигнализирует уже существующему: связь ставится через `attach()`, а не через конструктор, и до привязки `poll()` ничего не делает. Часы машины спрятаны за `TimeSource` — это единственное место, где читается реальное время, и ядро этого заголовка не видит. Поток таймера появится вместе с окном; пока цикл — это `poll()`, который дёргает кто-то снаружи.

**Подсистем сейчас две.** `WeatherSystem` даёт температуру по кривой месячных узлов, `PlantSystem` — рост посевов по кривой коэффициентов. Погода идёт первой: атмосфера считается до того, что под ней растёт, и когда посевы начнут читать температуру, они увидят значение этого мгновения, а не предыдущего. Обе подсистемы — замкнутая форма: состояние есть функция мгновения, шаг только решает, когда значение обновится.

**Порядок внутри шага.** Сначала применяются накопленные сигналы, затем двигаются часы, затем подсистемы считают состояние на новый момент. Сигнал применяется на границе шага и никогда посреди него: применённый посреди шага, он сделал бы результат зависимым от момента прихода, а это ровно то расхождение, которое запрещено в ОД-34. Подсистема получает не только `dt`, но и часы: системе с замкнутой формулой нужно абсолютное время, и из одного `dt` его не восстановить.

**Режим ускорения переключает сам Evaluator,** получив сигнал: `BeginAcceleration` со сроком и `InterruptAcceleration`. Ускорение заканчивается исчерпанием срока или прерыванием, и в обоих случаях начинается новый ход (ОД-14). Выбор `dt` под срок ускорения пока остаётся снаружи: это открытый вопрос ОД-32/ОД-33, и Evaluator его не решает.

**Настройки игрока — не состояние мира, и Evaluator их не видит.** Яркость, громкость и горячие клавиши живут отдельным файлом в отдельной библиотеке `config`. Меняются они, пока игра стоит на паузе или не запущена, поэтому симуляции нечего на изменение реагировать. Направление зависимости и есть гарантия: `config` зависит от `core`, а `core` от `config` — нет, поэтому ни один файл симуляции не может назвать тип `Settings`. Раньше это сторожила проверка «два прогона с разными настройками дают одинаковый хеш»; теперь сторожит компилятор, что сильнее и не гниёт. Если какая-то настройка когда-нибудь *должна* влиять на исход, она перестаёт быть настройкой и переезжает в сценарий, где запись прогона её увидит.

**Порядок в хеше:** часы, затем каждая подсистема в порядке добавления, затем ГПСЧ мира. Подсистема считает свой хеш сама, поэтому забытое поле — её собственная ошибка, а не пропуск в одном общем списке. Режим и счётчик шагов в хеш не входят: это учёт прогона, а не мир. Счётчик шагов здесь особенно важен: один и тот же срок при разном `dt` даёт разное число шагов, и хеши обязаны совпасть. Проверка на сетке `dt` это и стережёт.

## Сезоны и рост

Сезон — это ярлык для месяца, который идёт: весна 3–5, лето 6–8, осень 9–11, зима 12, 1, 2. Он нужен человеку, интерфейсу и проверкам, но ростом он не управляет и никаких блоков суток не образует.

Рост задаётся кривой коэффициентов: по одному узлу на начало каждого месяца, между узлами линейная интерполяция, с переходом от декабря к январю. Коэффициент в сотых: 100 — полная скорость, −100 — растение теряет рост с базовой скоростью, 0 — стоит. Поэтому «растёт весной и летом, увядает осенью» перестало быть ветвлением по сезону и стало значениями в таблице.

**Почему форма важнее чисел.** Все месяцы одинаковой длины (ОД-31), поэтому интеграл кривой считается в замкнутом виде. Значит, рост посева — **функция мгновения**, а не накопленная сумма: `рост = базовая скорость × (C(сейчас) − C(посев)) / 100`, где `C` — интеграл коэффициента от начала года. Два прогона, пришедшие в один момент, держат одинаковые посевы, как бы они ни резали время по дороге. Проверка — два сценария, считающие одни и те же четверо суток шагом в секунду и шагом в час: у них один ожидаемый хеш.

**Что от этого сломалось и осталось сломанным.** Увядание упирается в ноль, и `max(0, …)` от функции всё ещё функция мгновения, так что и это предсказуемо. А вот смерть — нет: погибшее растение не должно оживать, когда интеграл снова уходит в плюс, а «остаться мёртвым» в функцию мгновения не выражается. Для смерти нужны собственное состояние и событие, которое его переключает. Это первая вещь в мире, которая по-настоящему непредсказуема.

## Ускорение: предсказуемые и непредсказуемые системы

Идея автора: разделить системы мира на линейные и нелинейные. Линейные считают свой прирост по **графу предсказания**, который строится в момент нажатия кнопки ускорения, и во время ускорения их можно вообще не итерировать — пока не случится необычное событие: набег, пожар, паводок.

**Что здесь работает.** Система, у которой состояние есть функция мгновения, не требует шагов вовсе: достаточно вычислить её в нужные моменты. Посевы теперь именно такие, и это не совпадение — замкнутая форма появилась вместе с кривой коэффициентов, потому что обе опираются на одинаковую длину месяцев.

**Что требует уточнения.** Деление «линейные / нелинейные» не совпадает с делением «предсказуемые / непредсказуемые», а работать надо со вторым. Система может быть нелинейной и всё же предсказуемой: кривая с изломом, ограничение сверху, порог — всё это предсказуемо, если момент излома вычисляется. Мы уже так делаем внутри шага, деля его по границе сезона; при ускорении то же деление работает на другом масштабе — по границам событий, а не шагов. Непредсказуемо только то, что зависит от истории: смерть растения, столкновения, решения управляющих.

**Как это выглядит в работе.** Ускорение становится циклом: предсказать до ближайшего события, зафиксировать состояние, применить событие, предсказать снова. Событие обрывает предсказание с того момента, когда случилось, поэтому «не итерировать, пока не случится необычное» — это и есть корректная формулировка, а не упрощение.

**Чем это проверяется.** Тем же способом, что и всё остальное: пропуск, посчитанный предсказанием, и тот же срок, пройденный шагами, обязаны дать одинаковый хеш. Машинерия сценариев для этого уже есть, и именно она покажет, где предсказание врёт.

**Что не решено.** Какие системы на самом деле предсказуемы, как устроен граф предсказания и как событие обнаруживается посреди пропуска, если система в это время не считается. Последнее — самое неочевидное: чтобы поймать событие, его условие всё равно надо проверять, а значит, часть работы во время ускорения никуда не исчезает.

## Что ещё не решено

- Конкретный порядок вызова подсистем — после того, как сложится список специализированных классов.
- Форма коллайдера для каждого типа объекта и нужны ли составные коллайдеры.
- Вращается ли коллайдер вместе с объектом.
- Полная матрица поведений по парам типов — контент, наполняется по мере появления типов.
- Пространственная структура: нужна для broad phase столкновений. Для снимка может и не понадобиться, если полный снимок компактных структур окажется достаточно дешёвым.
- Порядок разрешения конфликтов между изменениями, пришедшими из разных очередей.
- Ограничение размера очереди повторного обновления.
- Интерполяция отрисовки между снимками: для M1 не нужна, для демо нужна.
- Поведение очереди снимков, когда поток отрисовки не успевает за шагами.
- Подшаги внутри системы допустимы. Их число должно быть фиксированным, чтобы результат не зависел от того, на какой машине шёл прогон.
- Независимость решения управляющего от порядка обхода его графа: проверяется прогоном в нескольких допустимых порядках.
- Туман войны в движке: видимость считается отдельно для каждого игрока, включая лагеря бандитов. Открыто, как именно она вычисляется и входит ли в хешируемое состояние.
- Когда генерируется карта — целиком до старта или частями в игре: от этого зависит, держит ли движок весь мир. См. ОД-30.
- Значение `dt`: оно задаёт и плавность 1×, и цену ускорения. Сколько шагов стоит сезон при разных `dt` — посчитано в ОД-32. При ускорении шаг предлагается менять по расписанию — см. ОД-33.
- Снимок и туман: скрытое либо не попадает в снимок, либо отрисовка сама накладывает туман по данным видимости. То же касается мини-карты — она показывает только разведанное.

## Тонкое место: снятие паузы

Ожидание до следующего шага считается относительно замеренной длительности предыдущего шага (пункт 4). В этом случае после длинной паузы догоняющих шагов не возникает — цикл просто продолжает с обычным интервалом.

Если же ожидание когда-нибудь начнёт считаться от абсолютного расписания, пауза в пять минут создаст очередь примерно из 6000 шагов при 20 Гц. Такую очередь нужно **отбрасывать**, а не выполнять: иначе при снятии паузы игровое время скачком уйдёт вперёд. При снятии паузы расписание пересобирается от текущего момента.
