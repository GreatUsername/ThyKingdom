# Цикл симуляции

Как устроен шаг симуляции и как в него попадают изменения игрока. Записано со слов автора;
следствия для рубежей — в [[02 Milestones]], для решений — в [[05 Open decisions]].

## Как устроено

1. **Поток таймера.** Следит за машинным временем и бросает колбэк, когда машинное время
   изменилось на величину, заданную при запуске приложения.
2. **Рабочий поток.** Получает колбэк и считает, сколько ждать до начала следующего шага
   симуляции.
3. **Шаг симуляции.** По истечении ожидания выполняется шаг.
4. **Замер.** По завершении шага рабочий поток измеряет, сколько шаг занял, сохраняет
   значение и считает время ожидания до следующего шага.
5. **Окно изменений.** Между шагами состояние игры может меняться, и изменения применяются
   до следующего шага. Пока шаг выполняется, изменения игрока копятся в очереди; из очереди
   они применяются в промежутке между шагами. UI — инструмент, который кладёт изменения
   в эту очередь.

## Что из этого следует

**Пауза — это отсутствие шагов.** Это состояние цикла, а не игровое правило: шаги просто не
планируются. Поэтому пауза ничего не стоит и не требует отдельных механик. См. ОД-16.

**Ускорение — это изменение расписания, а не правил.** N шагов остаются N шагами, как бы
быстро они ни выполнялись.

**Приказы не трогают состояние напрямую.** Единственный вход в состояние — очередь,
разбираемая на границе шага. Значит, порядок разбора обязан быть детерминированным
(например, FIFO с устойчивым разрешением совпадений).

**Запрет приказов во время ускорения — это правило игры, а не ограничение движка.**
Очередь технически принимает изменения в любой момент, включая ускорение. Запрет из ОД-14
накладывается сверху, на уровне UI и правил.

## Пауза

Реализуется флагом в состоянии игры. После того как колбэк получен и ожидание истекло,
цикл перед шагом проверяет флаг: если состояние помечено как приостановленное, симуляция
живых событий не выполняется — шаг пропускается.

Отсюда два полезных свойства:

- **Пауза — решение на границе шага.** Она не может застать шаг в середине, поэтому не
  портит состояние и не требует отдельных правил.
- **Пауза не обязана попадать в лог команд.** Она меняет расписание, а не содержимое шагов;
  при отсчёте игрового времени по числу шагов воспроизведение от неё не зависит.

Задержка срабатывания паузы ограничена одним интервалом шага.

## Единственное правило, без которого всё рассыпается

> **Игровое время обязано быть функцией числа шагов, а не машинного времени.**

Если это выполнено, то пауза, 1× и N× — одна и та же симуляция с разным расписанием, и
результат у них совпадает. Это и есть требование «корректной связи времени и событий» из
[[Время в игре]], выраженное проверяемо.

Отсюда два запрета:

1. Внутри шага симуляции нельзя читать машинное время. Любое «растёт три реальные секунды»
   ломает воспроизводимость и делает ускорение меняющим результат.
2. Замеренная длительность шага (пункт 4) годится для диагностики и планирования, но не
   может влиять ни на состояние игры, ни на число выполняемых шагов.

## Как решения выражаются в цикле

| Решение                                      | Выражение в цикле                                                                   |
| -------------------------------------------- | ----------------------------------------------------------------------------------- |
| ОД-14: приказы недоступны во время ускорения | политика поверх механизма: очередь принимает всегда, запрет — правило игры          |
| ОД-15: срок ускорения выбирает игрок         | UI-бокс задаёт бюджет шагов; «дни или месяцы» — отображение бюджета в игровое время |
| ОД-16: пауза при открытии меню               | меню просит цикл не планировать шаги                                                |
| 86: время хода идёт 1:1                      | штатное расписание: один шаг за один интервал реального времени                     |
| 88: хардмод без прерывания                   | запущенный бюджет шагов нельзя отменить                                             |

## Что ещё не решено

- Частота шага — см. ОД-17.
- Точка разбора очереди на границе шага и порядок разрешения конфликтов между изменениями.
- Интерполяция отрисовки между шагами: для M1 не нужна, для демо нужна.
- Подшаги для коллизий: если понадобятся, их число тоже должно быть фиксированным.

## Тонкое место: снятие паузы

Ожидание до следующего шага считается относительно замеренной длительности предыдущего
шага (пункт 4). В этом случае после длинной паузы догоняющих шагов не возникает — цикл
просто продолжает с обычным интервалом.

Если же ожидание когда-нибудь начнёт считаться от абсолютного расписания, пауза в пять
минут создаст очередь примерно из 6000 шагов при 20 Гц. Такую очередь нужно
**отбрасывать**, а не выполнять: иначе при снятии паузы игровое время скачком уйдёт
вперёд. При снятии паузы расписание пересобирается от текущего момента.
