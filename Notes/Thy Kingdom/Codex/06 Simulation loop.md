# Цикл симуляции

Как устроен шаг симуляции и как в него попадают изменения игрока. Записано со слов автора;
следствия для рубежей — в [[02 Milestones]], для решений — в [[05 Open decisions]].

## Как устроено

1. **Поток таймера.** Следит за машинным временем и бросает callback, когда машинное время изменилось на величину, заданную при запуске приложения.
2. **Рабочий поток.** Получает callback и считает, сколько ждать до начала следующего шага
   симуляции.
3. **Шаг симуляции.** По истечении ожидания выполняется шаг.
4. **Замер.** По завершении шага рабочий поток измеряет, сколько шаг занял, сохраняет
   значение, засыпает до следующего callback.
5. **Окно изменений.** Между шагами состояние игры может меняться, и изменения применяются до следующего шага. Пока шаг выполняется, изменения игрока копятся в очереди; из очереди они применяются в промежутке между шагами. UI — инструмент, который кладёт изменения в эту очередь.

## Потоки

| Поток               | Что делает                                                                    |
| ------------------- | ----------------------------------------------------------------------------- |
| Таймера             | Следит за машинным временем и бросает callback                                |
| Рабочий (симуляция) | Ждёт, выполняет шаг, замеряет длительность, засыпает до следующего callback   |
| UI                  | Живёт отдельно и продолжает работать при паузе                                |
| Отрисовки           | Берёт снимок состояния и строит кадр                                          |

**Снимок состояния для отрисовки.** Когда шаг выполнен, состояние кладётся в
потокобезопасную очередь. Поток отрисовки забирает снимок из очереди, когда ему удобно, и
строит по нему кадр — это происходит, пока симуляция находится в ожидании. Благодаря этому
отрисовка не блокирует симуляцию: блокировки на обновление кадра нет.

**UI живёт в своём потоке.** Поэтому при паузе интерфейс продолжает работать, хотя симуляция
живых событий не выполняется.

## Мир как композиция подсистем

`World` — класс, который содержит специализированные классы, реализующие общий базовый
интерфейс:

| Подсистема                               | Что содержит                                                  |
| ---------------------------------------- | ------------------------------------------------------------- |
| Поверхность (surface)                    | рельеф, клетки, земля                                         |
| Атмосфера и погода (atmosphere, weather) | температура, осадки, сезоны                                   |
| Объекты (objects)                        | контейнер указателей на базовый класс — все объекты симуляции |

`World` работает с подсистемами через базовый интерфейс и заставляет их выполнять шаг
симуляции и взаимодействовать между собой. Логика живёт в подсистемах, а `World` — это
координатор.

## Обновление мира внутри шага

Обновление сущностей (юнитов, зданий, ресурсов) идёт очередью. Если при обновлении сущность
воздействует на другую сущность, то та, на которую направлено воздействие, кладётся в
**очередь повторного обновления**.

Эта очередь вызывается после того, как основная очередь сущностей закончила обновление, —
в рамках того же шага. А взаимодействие, возникшее уже при повторном обновлении, будет
обработано следующим обновлением мира, то есть при вызове нового шага симуляции.

Схема ограничивает каскад взаимодействий одним дополнительным проходом на шаг и потому
остаётся детерминированной.

Очередь не одна. У каждой своё назначение:

| Очередь              | Кто кладёт                                  | Когда разбирается                   |
| -------------------- | ------------------------------------------- | ----------------------------------- |
| Изменения от UI      | UI                                          | между шагами, перед следующим шагом |
| Обновление объектов  | шаг симуляции                               | внутри шага                         |
| Повторное обновление | объекты, воздействовавшие на другие объекты | внутри того же шага, после основной |

### Риск: порядок обхода контейнера объектов

Контейнер указателей обходится на каждом шаге, и **порядок обхода — это порядок симуляции**.
Если порядок зависит от значений указателей — например, контейнер упорядочен по адресу или
это хеш-таблица с ключом-указателем, — результат перестаёт воспроизводиться: адреса меняются
от запуска к запуску из-за рандомизации адресного пространства.

Безопасный вариант: объекты лежат плотным массивом и имеют устойчивый идентификатор; обход
идёт по идентификатору или по индексу в массиве. Указатели остаются для доступа, но не для
упорядочивания.

## Что из этого следует

**Пауза — это отсутствие шагов.** Это состояние цикла, а не игровое правило: шаги просто не
планируются. Поэтому пауза ничего не стоит и не требует отдельных механик. См. ОД-16.

**Ускорение — это изменение расписания, а не правил.** N шагов остаются N шагами, как бы
быстро они ни выполнялись.

**Приказы не трогают состояние напрямую.** Единственный вход в состояние — очередь,
разбираемая на границе шага. Значит, порядок разбора обязан быть детерминированным
(например, FIFO с устойчивым разрешением совпадений).

**Запрет приказов во время ускорения — это правило игры, а не ограничение движка.**
Очередь технически принимает изменения в любой момент, включая ускорение. Запрет из ОД-14 накладывается сверху, на уровне UI и правил.

## Пауза

Реализуется флагом в состоянии игры. После того как callback получен и ожидание истекло,
цикл перед шагом проверяет флаг: если состояние помечено как приостановленное, симуляция
живых событий не выполняется — шаг пропускается.

Отсюда два полезных свойства:

- **Пауза — решение на границе шага.** Она не может застать шаг в середине, поэтому не
  портит состояние и не требует отдельных правил.
- **Пауза не обязана попадать в лог команд.** Она меняет расписание, а не содержимое шагов;
  при отсчёте игрового времени по числу шагов воспроизведение от неё не зависит.

Цикл живых событий при паузе не двигается вперёд вообще: шаги не выполняются, игровое
время не течёт. Работает только UI — потому что он живёт в своём потоке.

Задержка срабатывания паузы ограничена одним интервалом шага.

## Единственное правило, без которого всё рассыпается

> **Игровое время обязано быть функцией числа шагов, а не машинного времени.**

Если это выполнено, то пауза, 1× и N× — одна и та же симуляция с разным расписанием, и
результат у них совпадает. Это и есть требование «корректной связи времени и событий» из
[[Время в игре]], выраженное проверяемо.

Отсюда два запрета:

1. Внутри шага симуляции нельзя читать машинное время. Любое «растёт три реальные секунды» ломает воспроизводимость и делает ускорение меняющим результат.
2. Замеренная длительность шага (пункт 4) годится для диагностики и планирования, но не
   может влиять ни на состояние игры, ни на число выполняемых шагов.

## Частота шага

Частота определяется **перед запуском игры**, по характеристикам производительности машины
(ОД-17). Одна игровая секунда во время хода равна одной реальной секунде, но симулируется не
одним шагом, а частотой шагов: при 60 Гц — 60 шагов за игровую секунду.

Отсюда шаг игрового времени был бы равен `1 / частота`. **Но по ОД-18 из частоты шаг не
выводится:** шаг фиксирован в данных, а частота — это такт, то есть сколько шагов машина
успевает выполнить за реальную секунду.

Следствие: при фиксированном шаге прогон переносится между машинами как
`(seed + поток команд + число шагов)`. Мультиплееру (статус `parked`) понадобилась бы общая
фиксированная частота.


### Шаг и такт — это два разных параметра

| Параметр   | Что задаёт                                    | Может зависеть от машины          |
| ---------- | --------------------------------------------- | --------------------------------- |
| Шаг (`dt`) | сколько игрового времени прибавляет один шаг  | **нет**, иначе симуляция разная   |
| Такт       | сколько шагов выполняется за реальную секунду | да, это и есть производительность |

**Решено (ОД-18): шаг фиксируется в данных, от машины зависит только такт.** Симуляция
становится одинаковой везде: слабая машина просто реже выполняет те же самые шаги.

Что остаётся решить — уже не вопрос детерминизма, а вопрос поведения при нехватке
производительности: замедление игрового времени, догоняющие шаги или минимальные
требования. Варианты и рекомендация — в [[05 Open decisions]], ОД-19.

## Как решения выражаются в цикле

| Решение                                      | Выражение в цикле                                                                                                |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| ОД-14: приказы недоступны во время ускорения | политика поверх механизма: очередь принимает всегда, запрет — правило игры                                       |
| ОД-15: срок ускорения выбирает игрок         | UI-бокс задаёт бюджет шагов; «дни или месяцы» — отображение бюджета в игровое время                              |
| ОД-16: пауза при открытии меню               | меню просит цикл не планировать шаги                                                                             |
| 86: время хода идёт 1:1                      | одна игровая секунда равна одной реальной и симулируется частотой шагов (при 60 Гц — 60 шагов), а не одним шагом |
| 88: хардмод без прерывания                   | запущенный бюджет шагов нельзя отменить                                                                          |

## Что ещё не решено

- Порядок вызова подсистем внутри шага (погода → поверхность → объекты?) и то, как подсистемы
  взаимодействуют: напрямую или только через `World`.
- Хранение объектов: плотный массив с идентификаторами или отдельные аллокации под указателями.
  От этого зависит и порядок обхода, и стоимость снимка для отрисовки.
- Чем ищутся соседи для коллизий и взаимодействий: сетка, пространственный хэш или линейный
  перебор.
- Что попадает в снимок для отрисовки: полная копия состояния, двойная буферизация или
  отдельная компактная модель для отрисовки.
- Порядок разрешения конфликтов между изменениями, пришедшими из разных очередей.
- Ограничение размера очереди повторного обновления.
- Интерполяция отрисовки между снимками: для M1 не нужна, для демо нужна.
- Поведение очереди снимков, когда поток отрисовки не успевает за шагами.
- Подшаги для коллизий: если понадобятся, их число тоже должно быть фиксированным.

## Тонкое место: снятие паузы

Ожидание до следующего шага считается относительно замеренной длительности предыдущего
шага (пункт 4). В этом случае после длинной паузы догоняющих шагов не возникает — цикл
просто продолжает с обычным интервалом.

Если же ожидание когда-нибудь начнёт считаться от абсолютного расписания, пауза в пять
минут создаст очередь примерно из 6000 шагов при 20 Гц. Такую очередь нужно
**отбрасывать**, а не выполнять: иначе при снятии паузы игровое время скачком уйдёт
вперёд. При снятии паузы расписание пересобирается от текущего момента.
